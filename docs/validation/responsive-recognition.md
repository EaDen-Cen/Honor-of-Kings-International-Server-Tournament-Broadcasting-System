# OCR 期间的操作响应与末手换英雄

本轮基线是已合并 #117 的 main `751b2c8`。验收时分别记录从导播操作到持久化 ACK、单次图片请求到候选返回、游戏画面变化到末手 Pick 确认，以及到最终阵容确认的耗时。每组都看最大值与超过目标的次数。100 ms 是端到端目标，完整工作流仍有超时样本。

## 导播操作

1. 在 Control 启用窗口识别。候选出现在采集面板中时，可以继续修改比分、使用其他面板或输入文字。打开手动 BP 输入会取消在途识别，收起后可继续自动监控。
2. 末手 P5 若显示本队已选英雄，核对同一画面的五个位置。只有五个清晰、不同、合法的英雄包含前四手时才产生唯一的新候选。自动提交还要满足稳定性和锁定标记要求。证据不足时使用人工确认。原始 Pick 保留先后顺序，最终归属单独提交。
3. 在「帮助 → 操作指南 / 版本」查看最近一次和本次会话最高的成功操作确认耗时。对于断线或没有收到确认的请求，沿用超时与重新连接提示。

## 在 Windows 上复测

在 `vite-project` 运行以下命令。操作确认基准会启动专用回环服务，使用临时比赛存档。并行模式在发送比分操作前启动完整 GHUD 图片请求，同时测量 WebSocket 心跳。每个场景预热八次，再记录四十次。报告中单列预热、计时样本峰值和达到或超过 100 ms 的次数。

```powershell
npm run benchmark:action-ack -- --during-hud
node --import tsx scripts/benchmark-recognition-http.ts
npm run test:e2e -- e2e/bp-frame-sampling.spec.ts e2e/control-capture-races.spec.ts e2e/final-pick-swap.spec.ts
```

逐帧复测时记录视频帧率、起始帧、末手 Pick 的 ACK、最终归属的 ACK 和两队显示结果。回放中提供的合成视频经过真实 HTTP、模板匹配和 Store。导播现场的全链路还包含游戏输出、采集设备、网络和磁盘。

## Windows 测量结果

| 场景与计时边界 | 样本 | 结果 |

文件同步时服务继续处理其他连接，正式操作仍在写盘成功后才确认。关掉候选审核或打开手动 BP 可以接管，迟到的旧识别结果会失效。末手恢复保留了新帧、英雄池、候选稳定性与锁标检查。另一个锁标压在头像上的合成样本在基线和新版中都进入人工核对。

以上数据来自 Windows 本机。末手秒锁换英雄尚缺当场原始录屏，真实模拟器截图的测量从已采到的帧开始。公网中转、实际采集等待和 OBS 满载都需要在导播机上计时。100 ms 的全链路最高延迟尚未达到。

## 回归结果

- Windows 构建、格式、lint 通过。lint 保留投票视图的两条既有 Fast Refresh 警告。补入小锁标回归后，单元及服务测试 432 项通过，2 项私有实录样本未提供。
- Windows Chrome 完整 Playwright 129/129 通过，耗时 13.9 分钟。`d24cd34` 的末手真实引擎用例另跑 6/6 通过。延迟报告使用每次实测耗时，功能断言检查实际已保存的英雄及归属。
- 首轮 Linux 浏览器回归 127/129。两项末手测试均识别出正确英雄，但小勾旁的队色菱形未通过背景检查。保留原测试画面，增加了对头像下方外扩区中菱形四轴及四角的校验。用三个失败裁图直接回放，全部从拒识恢复为勾号。以全池 120 张头像构造的 1440 个离线负例中，新规则未引入误判。
- Windows 进程所有权、启动器生命周期、异常退出隔离和模拟中转检查均通过。慢写盘集成测试验证了备份、导出、正常关闭和重启时的最终比分及操作 ID。
