## 1. 本轮用户实测反馈

真实操作发现三个高优先级问题：

1. **BP 录入速度跟不上实际游戏。**
   - 游戏里的 Ban/Pick 节奏很快，导播在当前 Control 页面里找英雄、确认当前阶段、再点击英雄，来不及同步录入。
2. **选手个人图片不显示。**
   - V2.2 虽然已经增加 `playerPortraits`、预览组件和 Overlay fallback，但真实使用时没有正常看到选手个人形象。
3. **Control 操作时无法同时看到 BP 面板与英雄选择器。**
   - 当前 Control 页面是纵向文档流：Board → 操作条 → Lifecycle → Hero Picker。
   - 滚动到英雄池后，上面的比赛/BP 面板离开视野；回去看面板又看不到英雄池。

这三项应该作为 V2.3 的核心任务，优先于新的视觉功能。

# 3. 代码级模拟：一次 BP 点击目前发生什么

当前 Hero Picker 点击英雄：

```text
用户点击英雄
↓
BroadcastApp -> send(draft_action)
↓
useMatch 创建 action id
↓
pending = true
↓
WebSocket 发送 {revision, action}
↓
server/store.ts 验证当前 phase / hero / BP rule
↓
state.currentPhase++
↓
revision++
↓
立即广播新 snapshot
↓
Control 切换到下一 phase
```

关键点：

- **没有人工倒计时。**
- **没有 staged / pending hero。**
- **没有确认按钮。**
- 点中合法英雄就直接推进 phase。
- `useMatch` 在收到 ACK/更新之前只允许一个 pending action，这是正确的并发保护，不应为了“更快”删除。
- Server 本身的 phase 推进很直接，问题主要不是 Server 慢，而是**导播录入界面的人机效率不够高**。

因此不要用“给 BP 人为加延迟”解决问题。真实比赛不会因为我们的网页变慢。

正确方向是：**减少导播寻找英雄和切换视线的时间。**

# 4. 问题一：BP 操作速度跟不上

## 4.1 当前根因

当前 Hero Picker 有搜索框、位置筛选和英雄大网格，但：

- Search 不会在每次选择后自动清空。
- Search 不会自动重新获得焦点。
- 没有键盘快速录入。
- 没有“一眼看当前阶段 + 一手输入”的 Operator Cockpit。
- Board 和 Hero Picker 不在同一视野内，这会进一步浪费时间。
- Hero Grid 包含完整英雄池，导播如果纯鼠标寻找英雄，实战会明显吃力。
- 每次 phase 更新后，用户仍要确认现在是哪方 Ban / Pick。

## 4.2 不要这样修

不要：

- 给服务器 phase 自动加 2–3 秒等待。
- 每次英雄点击再弹 Confirm 对话框。
- 去掉 revision/pending 防重复机制。
- 让客户端乐观地连续发送多条尚未确认 revision 的 action。

这些方案会降低可靠性或让导播更慢。

## 4.3 建议新增“导播快速录入模式”

建议 Control 在 BP 期间进入专门的 `operator cockpit`。

### 当前阶段必须非常醒目

始终固定显示：

```text
BLUE BAN 1/4
RED PICK · Player 3: Nova
Phase 8 / 18
```

颜色随 blue/red。

不能要求用户滚动到 Board footer 才知道下一步。

### 搜索框保持焦点

当一次合法 Draft Action 成功后：

1. 自动清空 Search。
2. 自动 focus Search。
3. 用户可直接打下一个英雄名称。

注意：应在**服务器确认 action 后**清空/聚焦，而不是发送前。

### 键盘快速操作

建议：

- `/` 或 `Ctrl+K`：聚焦英雄搜索。
- `Esc`：清空搜索。
- 搜索结果只剩 **1 个合法英雄** 时：
  - `Enter` 直接提交该英雄。
- 结果 >1 时 Enter 不提交，避免误选。
- 鼠标点击仍然保留。

搜索必须继续支持：

- 中文名
- 英文名
- aliases

如果 Hero 数据已有拼音 alias，可自然支持；不要为了此任务硬加重量级模糊搜索依赖。

### 选择成功后视觉反馈

英雄提交成功后短暂突出：

```text
已记录：RED BAN · HeroName
下一步：BLUE PICK · Player 2
```

1000ms 左右即可，不要阻止下一步输入。

# 5. 问题三：Control 无法同时看 BP 面板和 Hero Picker

这是问题一的主要放大器。

## 5.1 当前 DOM 结构问题

`BroadcastApp.tsx` 当前大致：

```text
Board
↓
Operator Bar
↓
Settings（可展开）
↓
DraftLifecycle
↓
Hero Picker
↓
DraftHistory
↓
Analysis
```

所有内容都在普通纵向页面流中。

桌面操作时只要滚到 Hero Picker：

- Board 看不到。
- 当前双方 picks/bans 看不到。
- 当前比分/队名不在视野里。
- 要上下滚动确认状态。

这不适合实战导播。

## 5.2 建议新建 ControlDraftWorkspace

不要改变 Caster/Overlay 结构。

仅对 `role === 'control'` 重组操作区。

建议桌面 >= 1200px：

```text
┌────────────────────────────┬───────────────────────────────────┐
│ STICKY MATCH MONITOR       │ HERO PICKER                       │
│                            │                                   │
│ Compact Board              │ Current Phase                    │
│ Picks / Bans / Score       │ Search                            │
│                            │ Filters                           │
│ Lifecycle                  │ Hero Grid                         │
│ Undo / Reset               │                                   │
│                            │                                   │
└────────────────────────────┴───────────────────────────────────┘
```

推荐：

```css
.control-draft-workspace {
  display: grid;
  grid-template-columns: minmax(420px, 0.8fr) minmax(620px, 1.2fr);
}

.control-monitor {
  position: sticky;
  top: 12px;
  align-self: start;
  max-height: calc(100vh - 24px);
}
```

Hero Picker 可以拥有自己的滚动区域：

```css
.control-hero-picker {
  max-height: calc(100vh - ...);
  overflow-y: auto;
}
```

核心验收目标：

> 在 1920×1080 和 1440×900 Control 窗口中，不滚动主页面即可同时看到当前 BP 面板和英雄搜索/英雄网格上部。

## 5.3 Board 应支持 compact variant

当前 `Board` 是普通大面板。

建议：

```tsx
<Board state={state} lang={lang} compact />
```

Compact Board 只保留导播真正需要：

- 队名
- 比分
- 5 Picks
- Current Bans
- 当前 Phase

减少大 padding / 大头像。

不要复制另一套比赛状态逻辑。

## 5.4 Settings 不应把现场操作界面向下推

当前 Settings 展开在正常文档流中，会把 Lifecycle / Hero Picker 往下挤。

建议桌面改成：

- drawer
- modal
- 或独立右侧浮层

至少在 BP 正在进行时，Settings 不应破坏 Operator Cockpit 的布局。

## 5.5 响应式

- Desktop：左右双栏 Cockpit。
- Tablet：上方 sticky compact board + 下方 picker。
- Mobile：仍然单列，但增加 sticky current-phase mini bar。

不要影响 `/overlay/draft` 的固定 1920×1080 Canvas。

# 6. 问题二：选手个人图片不显示

## 6.1 当前代码实际上已经有 Portrait 数据链

现在存在：

```ts
Team.playerPortraits: string[5]
```

Settings 中有：

- Player Portrait URL 输入框
- Preview
- HTTPS / 本地 `/playerImg/...` 验证

Overlay 中：

```text
未 Pick Hero
→ Player Portrait
→ 加载失败则 Team Logo
→ 再失败则 Slot Number
```

Pick Hero 后：

```text
Player Portrait
→ HeroReveal
→ Hero Art
```

因此“选手照片功能完全没写”不是事实。

## 6.2 真实使用失败的主要风险点

### A. 当前没有图片上传功能

Server 目前：

```ts
if (req.method !== 'GET') return 405
```

没有：

- upload API
- multipart API
- image library
- player image manager

Settings 只是让用户**输入一个字符串 URL**。

### B. 仓库的 playerImg 目录目前没有实际图片

当前：

```text
vite-project/public/playerImg/.gitkeep
```

没有真实选手照片。

所以填：

```text
/playerImg/player1.png
```

只有在该图片真实存在于 `public/playerImg/` 并且之后重新 build，让文件进入 `dist/playerImg/` 后才会工作。

### C. 当前 Server 静态文件来自 dist

`server/server.ts` 静态根目录：

```ts
const root = resolve(project, 'dist');
```

因此：

```text
public/playerImg/a.png
```

不是“运行时自动可用”。

它需要 Vite build 复制到：

```text
dist/playerImg/a.png
```

### D. 现有 E2E 没有验证真实本地选手照片

当前 V2.2 E2E 测 Portrait 时主要使用：

```ts
playerPortraits: heroes.slice(...).map(h => h.imageLink)
```

即拿现有英雄图片 URL 伪装为选手 Portrait。

Fallback 测试使用：

```text
/playerImg/missing.png
```

确认失败后回退 Team Logo。

**没有测试一个真实存在的 `/playerImg/real-player.png`。**

因此自动测试通过并不能证明真实选手照片部署流程可用。

# 7. Portrait 建议修复方案

建议不要继续要求导播自己手动把图片复制到 public → build → 填路径。

这是赛事软件，不应该把素材管理变成开发流程。

## 7.1 推荐：增加真正的 Control-only 图片上传

Settings 每位选手增加：

```text
[选择图片]
[当前预览]
[删除/清空]
```

仍保留 HTTPS URL 输入作为高级方式。

### Server

增加 Control-only 上传 endpoint，例如：

```text
POST /api/uploads/player-portrait
```

不建议把图片转成 Base64 放进 MatchState：

- 会让 match.json 变巨大
- WebSocket snapshot 变巨大
- Caster delay events 复制很多图片数据

建议：

1. 上传真实文件。
2. Server 存到：
   ```text
   data/uploads/player-portraits/
   ```
3. 返回：
   ```json
   { "url": "/uploads/player-portraits/<uuid>.webp" }
   ```
4. MatchState 仍然只保存 URL string。
5. Server 单独只读 serve `/uploads/player-portraits/`。

### 安全限制

至少：

- 仅 Control token 可上传。
- 限制 MIME：
  - image/png
  - image/jpeg
  - image/webp
- 最大建议 5 MB。
- 不使用原始文件名作为服务器路径。
- 随机 UUID 文件名。
- 禁止 path traversal。
- 不执行 SVG。
- 删除/替换时不要允许用户指定任意文件系统路径。

这样 Cloudflare 公网 Caster / Overlay 也可以加载同一图片。

## 7.2 如果本轮暂时不做 Upload

至少：

- Preview 显示明确状态：
  - Loaded
  - Loading
  - Failed / 404
- URL 失败时不要静默 fallback，让导播不知道 Portrait 本身坏了。
- 在 Settings 中显示实际请求 URL。
- 文档明确：
  ```text
  /playerImg/foo.png 必须真实存在于 dist/playerImg/foo.png
  ```

但这只能算临时修复。

# 10. 现有代码中额外发现的维护风险

## 两套 CSS 同时 import

当前：


这不是本轮必须全部重写，但开发 Control Cockpit 时要谨慎：

- 新 Control V2.3 样式优先集中到 `BroadcastApp.css` 或新的 `control.css`。
- 不要修改 `dist/assets/*.css`。

如时间允许，可把职责整理为：

```text
broadcast.css
→ global/base/control legacy primitives

BroadcastApp.css
→ current Control/Caster responsive

overlay.css
→ fixed 1920x1080 overlay only
```

但不要为了“整理代码”大规模改变视觉而引入风险。

# 13. 实战验收脚本

不要只跑自动测试。

真实导播彩排：

### 准备

- Control: 1920×1080 或导播真实窗口尺寸
- Overlay: OBS 1920×1080 Browser Source
- Caster: 另一台设备或手机
- Delay: 先设 0 秒验功能，随后设真实比赛值

### 彩排

1. 打开 Control。
2. 不滚屏，确认同时可见 Board + 当前 Phase + Search + Hero Grid。
3. 连续模拟真实比赛 18 个 Ban/Pick。

5. 切换红先手再做一次。
6. Global BP 第二局确认历史限制。
7. BP 开始前确认十张选手照片显示。
8. 每次 Hero Pick 确认 Portrait → Hero 动画。
9. OBS Panel 测试。
10. OBS Side 测试。
11. Cloudflare Caster 测试。
12. 记录实际操作过程中任何必须来回滚动、找按钮或重复点击的地方。

# 14. 本轮验收标准

V2.3 完成的最低标准：

### 操作效率

- 1920×1080 Control 可同时看到 BP 状态和英雄选择区。
- Search 不因 phase 变化丢失可操作性。
- 一次合法选择后自动准备下一次输入。
- 导播不需要为了确认 BP 状态上下滚屏。

### Portrait

- 至少一种**真实用户可执行的**照片配置流程，不依赖“拿 Hero URL 当测试图片”。
- 设置页明确显示图片加载失败。
- Overlay 未选 Hero 时正确显示 Portrait。
- Hero Pick 后正确进入现有 Reveal 动画。

### 稳定性

- 不破坏 authoritative Server。
- 不取消 revision/pending protection。
- 不破坏 BP rules / history / swap / first-pick。
- 不破坏 Caster delay。
- 不修改一键启动和 Cloudflare 逻辑，除非 Portrait runtime upload 确实需要 Server static route；此时启动器接口仍保持不变。

# 15. 特别提醒

这次不要把“BP 太快”理解为：

> 让程序变慢。

真正要求是：

> **让导播的录入路径变短。**

比赛 BP 的节奏来自游戏本身，网页应该追上比赛，而不是让比赛状态等待网页。

同时，“照片不显示”不能只靠再写一个 fallback 测试解决。当前最大的产品问题是：**没有真正的选手素材上传流程，而自动测试又没有覆盖真实本地选手图片成功加载。**

优先修实际赛事工作流，而不是继续堆功能。
