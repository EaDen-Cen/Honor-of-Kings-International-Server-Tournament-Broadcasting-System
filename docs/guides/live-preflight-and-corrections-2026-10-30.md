# 2026-10-30 · BO3 多局报告、已锁定英雄纠错与开播检查

## 已锁定 BP 槽位人工纠错

在 Control →「选禁工作区」展开「纠正已锁定英雄（人工优先）」：选择当前或历史局、蓝/红方、Ban/Pick、已录入的槽位和正确英雄，二次确认后发送 `replace_draft_hero`。示例：元流之子被误识别成孙尚香，找到对应的 Pick 槽位，改为真实英雄。**不必撤销后面所有 BP 步骤，也不必重开比赛**。

- 当前未提交 BP：改当前槽位与按英雄 ID 匹配的最终归属。
- 已提交当前局：同时改当前 BP、已保存 `draftHistory`、该局赛后报告英雄头像；保留十人评分、人头、经济、MVP 选择和系列赛比分。
- 已进入下一局：选择历史局，仅修正该历史记录和关联的赛后英雄，不干扰正在比赛的阵容；保存的局数和团队身份不变。
- 仍拒绝未曾出现的槽位、重复选择（含 Flowborn 共享形态）和不在所选服务器英雄池内的英雄。所有操作走原有 Control token、修订版本验证、持久化、历史快照和 Undo。修正已播出的画面**不会自动撤回观众看到的旧图**；Caster 的延迟原则照旧。人工纠错不代表任何 OCR 能做到 100% 准确。

## 第二局赛后数据

确认某局有效时（`commit_game`），系统自动建立该局十人赛后报告并选择为当前编辑报告。**第 2 局确认后自动进入第 2 局报告**，第一局已有数据不清空；不需要再手动「准备本局 10 人报告」。仍可从「编辑哪一局的赛后数据」切回历史局补录。

注意：`commit_game` 是“赛后确认本局有效”动作，并非比赛开始键。第 2 局未确认前，系统不会凭空创建可信的第 2 局赛后报告。不要把上一局报告作为本局输入。

## 本机 OBS 录制磁盘容量

Control →「OBS 导播工作区」自动每 30 秒向 **本机才允许** 的 `GET /api/v1/obs/storage` 查询录制磁盘。优先通过 OBS WebSocket v5 的 `GetRecordDirectory` 获取真正的录制路径，再由 Node 的 `statfs` 读取可用块 `bavail`，不是把项目所在的 C 盘当作 OBS 的输出盘。显示路径、GiB、容量百分比、来源；低于 **20 GiB 或 10%** 时警告。不能读取时明确报未知，绝不显示虚假 0 或 C 盘值。

OBS 未启动或 WebSocket 未连接时，可在**本机服务端环境**设置 `HOK_RECORDING_DIR=E:\\OBS Recordings` 作为显式兜底，路径需存在且真的是 OBS 实际录制位置。此时状态注明“configured”，不能冒充 OBS 已核实。此端点没有路径查询参数，也不控制 OBS。若 OBS 在另一台机器，读到的是**本机后端所处文件系统**，应将监控移到真实录制机；不可依据远程文件夹名推断可用容量。

## 每局启动流程（伪强制）

Control 顶部常驻「第 N 局开播流程」直到核对四项并确认，或使用“紧急跳过（保留警告）”。核对内容：队伍/P1–P5/规则、BP 截图与人工纠错、OBS 音频场景录制磁盘、备份/Overlay/远程访问。每局重新出现；只保存在本次浏览器 Session 中。采用**伪强制**而不是后台硬阻止：避免直播中 OBS 或网页故障时无法继续救场；紧急跳过明确标注未验证。

## 回归与局限

新增 Node 测试验证：人工改 Ban/Pick 不推进阶段、重复英雄和无效局回滚、已提交及历史报告同步但保留手工数值、连续两局报告自动选中与隔离、真正录制盘剩余空间计算。构建、Lint、Windows 原生 OBS 路径与真实磁盘检测仍需 Actions/实机验收；测试代码不能代表已经完成直播联调。
