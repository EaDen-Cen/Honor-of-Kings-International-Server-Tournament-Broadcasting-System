# 选手对齐、恢复、局内 HUD 与赛后 MVP

> **v1.0.0 Release Candidate（2026-10-10）**：选手对齐、备份恢复和赛后 MVP 基础链路已进入发布准备状态。**局内 HUD 仍处于测试阶段（Experimental）**：可用于彩排和 OBS 预览，但自动游戏 HUD 读取尚未实现；真实比赛长时间稳定性待实机验收；正式比赛须保留官方/人工比分兜底。

## 开局选手对齐（M12A）

1. 赛前填写双方五名选手的真实游戏 ID；队伍资料库仍保留原始阵容顺序。
2. 启用屏幕输入并在 Auto BP 中选择游戏窗口。选手识别复用这条窗口采集流，与英雄识别并行。
3. 后端启动时预加载随 npm 依赖安装的英文与简体中文 Tesseract 模型。模型在本机常驻，比赛中无需下载模型或请求远程 AI。启动后 `/api/v1/recognition/players` 返回 `ready` 才开始 OCR。
4. 正常比赛不需要先手填 x/y/width/height。选手 ID 区域会从已经校准好的 P1–P5 Pick 头像框自动推导；第一次升级到新布局会只清除旧版错误的 ID 小框，不影响 18 个英雄框。OCR 首次完全读不到文字时还会自动尝试更宽的文字区域。只有真实游戏 UI 与默认推导不符时，才展开“高级：选手 ID 区域校准”，用方向/宽高按钮微调；精确百分比输入放在二级折叠中。这里还提供独立的 **ID 区域预设**：可提前把当前 10 个 Player ID 裁剪框保存为命名预设、赛前一键载入、覆盖更新或删除。ID 预设只修改 `playerIds`，不会碰已经校准好的 18 个 Ban/Pick 英雄框；使用归一化坐标，因此同一画面比例下可跨窗口尺寸复用。
5. 系统从同一帧裁剪十个 ID。英文与简中使用独立常驻模型并行生成候选，避免中文被英文优先的混合模型误读成拉丁字母。先识别十个保留抗锯齿灰度的 soft 裁剪；本队已登记的 5 个 ID 可高置信度一一映射时立即返回。仅对尚未通过的队伍追加 threshold 170/190 候选。排列求解仍比较全局最佳和第二名方案，不降低歧义保护。界面显示“候选 ID 匹配度”，原始 OCR confidence 保留在调试 tooltip 中。
6. 双方均可信时通过 `set_player_slot_orders` 一次原子更新十个槽位，避免蓝方提交后红方结果被后续扫描替换；仅一方可信时可以单独更新该队。双方服务器顺序均一致后停止扫描，复核间隔为 100ms，同一时间最多一个 OCR 请求。低置信度保留现有顺序并显示“自动复核中”；后台识别期间仍可点击“采用建议”。采用当前可见方案会暂停自动对齐并丢弃迟到的 OCR 响应，避免覆盖人工选择。人工调整后也会出现“恢复自动识别”按钮：清空双方锁定状态并重新扫描，双方可信时一起恢复，不需要刷新页面或重开采集窗口。 如果同一队的同一个 P1–P5 排列连续两帧一致，但两帧各自只是不同槽位略低于单帧阈值，Control 会合并两帧各槽位的最佳匹配度；只有合并后仍满足原来的每槽 `.80`、平均 `.90`、margin `.06` 安全线才自动通过。这样不会降低单帧标准，只解决“顺序一直一致但自动复核永不结束”的边缘情况。

`bluePlayerSlotOrder` / `redPlayerSlotOrder` 表示“屏幕槽位 → 当前阵容索引”。英雄 assignments 继续按屏幕顺序保存；照片、角色、ID、Player BP 限制、有效局历史和赛后报告通过映射读取身份。下一局/重置 BP 清除当前映射，有效局记录保留当局映射；资料库不会被重排。

自定义本地模型可配置 `.env` 中的 `HOK_OCR_MODEL_DIR` 与 `HOK_OCR_LANGUAGES`，目录内放置未压缩的 `<语言>.traineddata`。默认启用 `chi_sim+eng`，各模型独立常驻；其他文字需要对应本地模型。不要把模型文件、真实参赛 ID、照片或运行数据提交到仓库。

识别前先在原始亮度上定位文字，再对文字范围增强对比度，最后放大并补白。不能先把整条宽区域缩到 40px 再 normalize：大量留白会参与百分位统计，低亮度笔画会被抹掉。回归测试包含故障截图中“听雨”的真实裁剪、左右对齐的低亮度英文 ID、空白区域以及原有赛后数字识别。

`npm run benchmark:players` 使用正式 API 的快速首轮、按队追加候选及排列求解，测量宽区域内低亮度英文 ID，双方正确自动对齐才算通过。`e2e/milestones.spec.ts` 另有真实本地 OCR 的“浏览器采集 → OCR → 双方服务器顺序更新”两秒内验收、后台扫描时人工采用建议、迟到响应不覆盖、恢复双方顺序，以及连续两帧边缘结果合并的回归测试。当前 Simulator 完整核查最佳实测约 **1.8 秒**；实机字体、缩放、硬件和首帧等待仍会影响耗时，这不是赛事机 SLA。

## Simulator 联动测试

BP Simulator 控制台现在按用途分成 **选手 ID 排序 → BP 模拟 → 角色交换** 三种测试。采集页仍保持为独立窗口，Control 应选择该采集页而不是 Simulator 控制页。

开启“Control 联动测试”是一个显式安全开关：浏览器无法可靠、跨端口确认 `getDisplayMedia` 当前究竟选中了哪个窗口，因此 Simulator 不会仅凭 Control 的“屏幕识别”状态就擅自改比赛。只有开启这个开关后，“重置进度”才会同时发送 `reset_draft`，选手 ID 测试才会把生成的赛前 10 人名单写入 Control。英雄 Pick、换英雄结果和 P1–P5 顺序**不会直接同步答案**，仍必须由 Control 从 Simulator 画面识别，以免测试失真。

选手 ID 排序测试流程：

1. 选择测试集：默认混合英文+简中，也可单独测试英文/数字/符号、OCR 易混淆字符、简中或日文。
2. 点击“随机 10 个 ID / 准备房间”。开启 Control 联动时，Simulator 先重置 Control Draft，再把这 10 个 ID 按双方各五人同步为赛前 roster；此时 P1–P5 仍是正常 roster 顺序。
3. 采集页显示自定义房间等待页面。点击 START 后，蓝方五人和红方五人**分别在各自队伍内部**随机排序，不会跨队交换；同时开始计时并进入 BP 画面。
4. Control 的 Player Slot Alignment 从 BP 画面 OCR ID 并更新 `bluePlayerSlotOrder` / `redPlayerSlotOrder`。Simulator 持有随机后的 ground truth，双方顺序完全一致时自动停止计时。
5. 每次随机函数都会避免得到完整 identity 顺序，确保测试真正发生了重排。

选手 ID 排序模式中的行始终保持完整不透明度；不会沿用普通 BP 未选英雄行的 38% 透明度，以免尚未 Pick 的选手名字也变暗。

默认本地 OCR 由独立常驻 `chi_sim` 与 `eng` worker 提供。日文假名测试页已提供，但应在 `HOK_OCR_MODEL_DIR` / `HOK_OCR_LANGUAGES` 配置 `jpn` traineddata 后再作为正式通过项；默认配置下它属于故障/扩展能力压力测试。BP 自动脚本还可在 3–6 秒等极限等待窗口中随机切换预选英雄；真正锁定前保留约 1.2 秒稳定候选窗口，锁定 cue 默认保留 1.1 秒，便于验证 Control 是否能在快速 Draft 中连续取到确认帧。

换英雄模式与 BP 识别完全独立：先配置 Simulator 的 10 个最终英雄，再点击“同步 Simulator 英雄配置到 Control”。这个按钮通过正常 Control actions 建立一套已完成的 Normal BP 测试基线，不经过 BP OCR，也不计入换英雄耗时。之后交换两个 Pick 槽时不会直接调用 `set_lineup_assignments`；只有 LineupAssignments 从采集画面识别出变化、Control assignments 与 Simulator ground truth 一致，计时才结束。

## v1.0.0 现场状态摘要

- Player ID：Simulator 完整核查最佳约 **1.8 秒**；连续边缘帧可做两帧一致性复核，正常单帧高置信度路径不增加等待。
- Auto BP：Simulator 约 **1.5–2 秒**随机选角压力窗口下可稳定出结果；真实 HOK/OBS 并发仍需赛事机彩排。
- 换英雄：与 BP 识别分离，可独立建立测试基线后从采集画面验证最终归属。
- HUD：**测试阶段**，不作为唯一官方比分源。
- MVP：投票/人工决定人选；程序负责快速组织并展示已采集的数据，不自动评判 MVP。

## 备份与恢复（M15）

后端每分钟检查数据变化，变更后备份；Control 的“备份与恢复”可查看状态、立即备份、导出比赛。最近 20 份完整备份位于数据目录的 `backups/`，覆盖比赛状态、队伍资料库、访问设置与上传媒体（选手照片及赛后字段证据）。完整备份包含私有访问凭据，保存权限为本机私有；比赛导出不包含 `access.json`。

在 `vite-project` 目录运行：

```bash
npm run recovery -- backup
npm run recovery -- verify data/backups/backup-xxx.json
npm run recovery -- export match-export.json
```

恢复/导入前停止后端，再运行：

```bash
npm run recovery -- restore data/backups/backup-xxx.json
npm run recovery -- import match-export.json
npm run server
```

`.env` 中的 `DATA_FILE` / `UPLOAD_DIR` 同样适用于这些命令。`verify` 检查版本、路径、大小与 SHA-256；实际 restore/import 还会在临时目录加载并验证保存的状态与资料库。运行中的后端锁会阻止恢复，避免磁盘状态与内存状态相互覆盖。文件替换失败时回滚已替换的文件。

比赛导入保留接收机器的访问凭据；完整备份恢复会恢复原凭据，旧分享链接也会重新生效。导入仅替换归档中的文件，不删除接收机器上的无关媒体。启动、停止、操作拒绝和备份失败记录于 `logs/operations.jsonl`，日志限制约 1 MiB 并保留一份旧文件，不记录请求内容、口令或 OCR 文本。

## 局内 HUD（M19 · Experimental / 测试阶段）

OBS 添加浏览器源 `/overlay/game-hud`，尺寸 1920×1080；使用与 BP Overlay 相同的访问方式。正常背景透明。

**发布警告：HUD 当前不是已完成正式验收的比分系统。** 人头、推塔和资源主要依靠导播人工维护；自动读取真实游戏 HUD 尚未实现，真实赛事机上的 OBS 长时间稳定性、画面遮挡、版本 UI 变化和误操作恢复仍需继续测试。正式比赛如启用 HUD，应保留官方观战 UI、裁判记录或其他权威比分来源作为兜底。

Control 展开“局内 HUD / 人头、推塔与资源”：维护双方人头与推塔，添加最多六种中立资源的名称、图标与计数，选择简约或完整密度。队名、Logo、系列赛比分、当前局数、BO 和赛事阶段读取比赛状态；局内统计独立保存，不会修改系列赛大比分。顶部撤销可回退误操作，刷新/重连会恢复服务器状态。

进入下一局或重置 BP 会将局内计数归零，保留资源类型与密度。当前阶段没有自动读取游戏内 HUD；后续自动候选、冻结与字段级回退仍待实机识别方案。因此 v1.0.0 将 Game HUD 作为 Preview / Experimental 功能发布。

## 赛后报告与 MVP（M20 基础采集链路）

1. 完成换英雄/身份确认并提交有效局，展开“赛后数据与 MVP”，准备本局十人报告。身份、照片、角色、英雄、局数在此时从有效局快照固定，下一局和临时替补不会修改旧报告。
2. 保持游戏结算界面打开，复用 Auto BP 的窗口采集。手动选择总览/生存/输出/团队页及所需字段。
3. 为当前页面、字段的十名选手分别校准数字区域；**按列出的选手身份对齐区域**。不同结算页可能换列、排序，默认矩形只是校准起点，不能直接信任其行顺序。
4. 点击“捕获当前页字段”。一次处理十个数字小区域，返回草稿候选、置信度和原始裁剪证据。检查后应用。OCR 值不会直接覆盖已经人工确认的字段。
5. 数字输入框失焦后保存人工修正，记为人工确认。各页字段合并到同一份报告，百分比范围和整数项由服务端校验。
6. 投票决定 MVP 后，在下拉框选择相应选手；`/overlay/mvp` 立即展示统一蓝/红模板。未选择时页面透明，可清空选择隐藏卡片。

卡片展示 ID、照片、队伍、英雄、K/D/A、评分和本局赛事信息；根据角色选择最多三个可靠亮点。亮点只是展示顺序，程序不会判断 MVP。OCR 置信度低于 85% 的字段不进入自动亮点或主要统计展示，人工确认字段除外；缺失字段显示“—”，其余可靠字段仍可展示。

当前已实现手动指定页与字段、批量本地 OCR、证据保存、草稿合并、人工修正、选择 MVP 和展示。自动判定页面类型/稳定画面、自动跨页面一致性校验和全队数据页尚未实现；已实现的手动采集与 MVP 展示仍须真实结算画面验收。
