# 识别延迟、OBS 图片与代码维护

## 操作上的变化

导播提示明确区分 BP 完成与比赛结束：阵容核对阶段提供局内 HUD 与 OBS 入口；「确认本局有效」仍在比赛结束后执行，再更新比分和开始下一局，保留有效比赛记录的原有规则。

导播指引新增「局内采集与 HUD」和「OBS 切镜与音源」入口。导航会展开目标所在的折叠面板，不卸载采集组件，也不会重新选择游戏窗口。

GHUD 仍然需要连接正确的游戏内容、确认七项选框、核对两次读数，才能自动播出。面板新增的采样耗时包括浏览器采集、传输和服务端处理，比单独显示 OCR 算法耗时更接近实机体验。截图仍只用于审核；冻结字段、时钟前进、置信度、异常跳变和两帧核验的要求保持有效。

结算页切换左右队伍时，保留数字草稿但清除十人的已确认对应关系；重新采集或逐人审核后才允许应用，防止旧方向的数据直接写入另一队。

## 为什么模拟与实机的耗时不同

完整路径为：游戏画面产生 → 浏览器采集/裁剪 → 编码与传输 → 图像预处理 → OCR/英雄匹配 → 多帧核验 → 服务器确认 → OBS 图片解码与动画。模拟测试如果只计其中一段，不能直接当作最终上屏耗时。

本次调整：

- 视频/截图直接裁成标准游戏内容，取消高分辨率原始画面的中间复制；原始画面预览仍提供完整画面供校准。
- 局内数据从同一帧裁出七张无损 PNG，上传校准区域，不再上传整张动画游戏画面。服务端校验区域尺寸、顺序、图像边界和空白输入，继续使用原有颜色处理、数字解析与核验规则。旧的整帧接口仍兼容。
- 英雄模板和独立数字 OCR worker 在服务启动时预热。数字 worker 失败不会禁用选手识别，下次调用仍可重试。
- 数字的批量识别结果较弱时，保留逐格重试；不再对同一张未处理图片重试两次。已达到置信度要求时，不再运行无用的第二个变体。
- 已知纯拉丁字符名单先使用英语模型；未解决的槽位仍进入全部语言及图像变体回退。混合语言及中文名单继续使用多语言首轮。
- 最终英雄归属按扫描完成时间调度：平时等待 500 ms，发现可信变更后等待 120 ms 做第二轮确认，保留最多两个并行槽位请求。初始视频尺寸变化属于正常取消，不附加网络故障退避；真正识别失败仍会退避。
- GHUD 按目标每秒一次，在上一任务结束后安排下一次，不积压旧画面，也不因一次慢任务错过整个定时周期。

换源、换局、选框变化、手动修改和过期服务器修订的保护仍然有效。缩短调度等待不代表允许不可靠结果直接写入比赛。

## OBS 原画资源

默认英雄目录中已有原画的 112 项均有本地 WebP 副本，最大边长 1600 像素。源网址保留在 `src/data/broadcastArtAssets.ts`，文件名包含内容摘要。只有当前英雄的原始网址与记录完全一致时才使用缓存；用户自定义图片、之后新增的英雄不会被旧缓存覆盖。显示原画和识别头像模板仍是两套资源。

揭幕或滑入前先异步解码目标图片。等待期间保留当前画面；撤销或再次换英雄会使旧的加载结果失效。动画完成不会再重建同一张图片节点。预解码缓存最多保留 12 张，避免 OBS 长时间运行后积累大量图片内存。

服务端允许内容摘要命名的原画及构建资源长期缓存，普通静态图片使用短期缓存和 ETag；页面入口每次校验，比赛 API 继续禁用缓存。赛后对位和 MVP 也复用本地原画。

维护图片资源时，在 `vite-project` 执行：

```sh
npm run hero:art-cache
npm run build
```

下载只在维护命令执行时发生，不会在生产构建或比赛切图时临时下载整套原画。更新英雄目录后应重新执行该命令，并把新资源和清单一同提交。

## 程序员维护与测量

关键注释说明采集上下文、取消/故障的区别、两帧校验、语言回退、资源失效和图片动画的约束。此次涉及的识别、OBS、面板模块采用统一 Prettier 格式；生成目录和大型图像样本不做机械排版。

```sh
npm run format
npm run format:check
npm run format -- src/control/ScreenInput.tsx
npm run benchmark:hud
npm run benchmark:hud -- --image game.png --regions regions.json
```

`regions.json` 使用与 `liveCaptureRects` 相同的七字段归一化坐标格式。提供自有截图时，应先去除窗口标题栏和黑边。基准会分别输出模型预热、首轮、后续读数中位数及请求体大小，不修改比赛。

回归包括完整图像输入与七张裁图的 OCR 输入等价性、无效裁图拒绝、数字重试次数、英语首轮和全部本地原画的摘要/尺寸检查；浏览器检查折叠面板导航、图片迟到与撤销、HTTP 缓存和运行中换英雄的两轮确认延迟。真实赛事机还应结合 OBS 编码负载、窗口大小、显示缩放和网络实际复测，不能用此处的固定样本替代。

## 固定样本测量（2026-10-20）

同一 HUD 叠加固定高细节背景，比较修改前的整帧 JPEG 接口处理与修改后的七张 PNG 裁图。各运行五次预热后读数取中位数，字段解析结果一致。此处服务端耗时不包含网络；高细节背景用于放大整帧传输和重复解码成本，不代表所有真实游戏画面。

| 项目 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 图片请求体 | 2,150,243 字节 | 43,504 字节 |
| 预热后服务端处理中位数 | 362 ms | 181 ms |
| 数字模型加载 | 首次调用时发生 | 启动预热 242 ms，单独计时 |

运行中的最终阵容切换测试保留两轮确认，连续三次的「变更到服务器确认」为 1,030、624、1,024 ms。该测试排除页面首次加载，包含采集、每槽模拟 35 ms 处理及真实服务器写入；不要将这些数字解读为真实赛事画面的准确率或所有硬件的延迟保证。

## PR #91 默认本地立绘与基准

Windows 准备阶段默认调用 `hero:art-cache`，再构建包含缓存清单的前端。下载记录按来源 URL 和内容摘要命名，原子更新清单，不删除旧内容寻址文件（已有 OBS 页面可能仍在引用）。只重用来源完全匹配的缓存；缺失默认立绘使用本地头像，显式人工图片覆盖保持有效。当前已知 112/112 立绘经过缓存验证。

新命令 `npm run benchmark:replay -- --iterations 100 --output artifacts/replay.json` 交错测量无缓存/区域缓存，报告 P50/P95/P99、准确字段数量、环境及素材 SHA-256。支持 `--fixtures-dir` 指定同格式录制截图资料。结果不能当成采集到 OBS 的实时视频指标；见 [本轮验证](../validation/pr91-validation.md)。
